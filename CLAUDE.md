# CLAUDE.md — contexte du projet « myteam »

> Lire ce fichier en premier : il évite de ré-analyser tout le code à chaque demande.
> **Le mettre à jour à chaque modification structurante** (route, champ d'état, action d'agent, décision d'architecture).

## But
Application de gestion de projets de développement par une **équipe d'agents IA** (Claude, Mistral, ChatGPT, Gemini, DeepSeek…). Tourne en local sur Windows 11 (usage actuel) ou sur un serveur Linux (plus tard). Langue de l'interface, des prompts et des commentaires : **français**.

## Stack et contraintes
- Backend : **Python 3.10+, bibliothèque standard uniquement** (aucun `pip install` ; ne pas en introduire sans décision explicite).
- Front : `static/index.html`, SPA **fichier unique** (HTML + CSS + JS, sans framework ni build), servie par le backend.
- Persistance : fichiers JSON dans `data/` (ignoré par git) : `users.json` (hash PBKDF2), `sessions.json`, `users/<user>.json` (**état complet** d'un utilisateur). Pas de base de données pour l'instant.
- Git/GitHub : **API REST GitHub** via `urllib` (pas de git local). Dépôt + token au niveau projet.
- Variables : `APM_PORT` (8000), `APM_HOST` (127.0.0.1), `APM_DATA`, `APM_ALLOW_REGISTER`, `APM_GITHUB_API` (tests), `APM_SUPERVISE_SECONDS` (passage du suivi, 60 ; 0 = désactivé), `APM_LOCK_TTL` (900 s : expiration d'un verrou sans activité de son détenteur), `APM_LOCK_ORPHAN` (120 s : verrou d'un agent sans travail en cours), `APM_LOCK_WAIT` (90 s : attente maximale d'un verrou dans une action). Windows : `start.bat` ; macOS : `start.command`.

## API (JSON, `Authorization: Bearer <token>`)
- `POST /api/register|login` → `{token}` ; `POST /api/logout`
- `GET /api/state` → `{rev, ser, state}` ; `GET /api/state?ser=N` → `{same:true}` si rien n'a changé (sondage du front, toutes les 2 s)
- `PUT /api/state` `{rev, state}` → `{rev, ser, state}` : le serveur **fusionne** l'état du navigateur avec l'état courant (voir ci-dessous) et renvoie le résultat.
- `POST /api/service/test` `{serviceId}` : appel minimal au service IA (valide la clé). Les clés API se créent dans la console du fournisseur (aucun flux OAuth public ne permet de les générer : vérifié pour Anthropic et OpenAI) ; le front guide la saisie (`keyset`) et teste aussitôt.
- `POST /api/manual/answer` `{id,text}` / `POST /api/manual/cancel` `{id}` : réponse (ou annulation) d'un échange **manuel** en attente.
- `POST /api/job` `{type, projectId, ...}` : lance un travail en arrière-plan (un thread). Types : `say{agentId,text}`, `run_task{taskId}`, `onboard{agentId}`, `sync`, `release{version,notes}` (publication), `rules_changed`, `rules_check`, `workflow_run{wfId,task,note}`, `wf_resume{runId}`, `wf_stop{runId}`, `cycle_start{version}`, `mr_retry{mrId}`, `mr_done{mrId}`, `mr_sync`, `reset_usage`, `decide{decisionId,decision:accept|refuse|answer,note,fields,answer}`, `instr_add{scope,text}`, `instr_del{instrId}`. Le front fait `flush()` (PUT) avant chaque travail.

## Concurrence navigateur / serveur (important)
Le navigateur et le moteur modifient le même état. `store.put` fait une fusion **à trois voies** : base = dernier instantané reçu par le navigateur (`rev`, 8 gardés + celui servant de base), theirs = état disque, mine = état envoyé. Les listes d'objets avec `id` sont fusionnées par id (suppressions locales respectées, créations serveur conservées) ; en cas de vrai conflit sur une valeur, **le navigateur gagne**. Conséquences :
- Tout nouvel élément de liste doit avoir un `id`. Les listes sans `id` (`log`, `commits`, `history`…) sont écrites **uniquement par le serveur**.
- Champs écrits par le serveur : `log, commits, mrs, releases, cycle, conflicts, spec, releasing`, `agent.{history,notes,work,state}`, `task.{running,result,retry_at,stopped}`, `locks`, `lock_wait`, tâches/bugs créés par les agents. Le navigateur ne doit pas les modifier (`ensure()` ne doit que **compléter** les champs manquants).
- Le front adopte l'état serveur (sondage ou réponse du PUT) sauf s'il a des modifications en attente ou une fenêtre modale ouverte.

## Modèle de données (état utilisateur)
`{services:[{id,name,url,kind,model,apiKey,account,pros,cons}], roles:[{id,name,desc,caps}], projects:[...]}`
- **Rôles globaux** : `st.roles` (comme `services`), définis une seule fois dans la vue **Rôles** du menu de gauche et réutilisables par tous les projets ; `agent.role` et les étapes de workflow `role:<id>` y font référence par `id`. Un rôle utilisé par un agent d'un projet quelconque ne peut pas être supprimé. **Plus de `p.roles`** : `store.migrate_roles` (appelée à chaque `load`/`mutate`/`get`/`put`) convertit les anciens états (rôles de même nom fusionnés, `agent.role` et `role:<id>` remappés ; idempotente). Côté serveur, `store.load`/`mutate` rattachent à chaque projet une référence en lecture seule `p["_roles"]` (jamais écrite sur disque : `wj` la retire) ; le code lit les rôles via `rights.roles_of(p)` / `project_rules.roles_of(p)`, **jamais `p["roles"]`**. Côté front : `D.roles`, `ensureG(D)` (migration/seed), helpers `role(p,a)` et `rname(p,id)`.
Projet : `{id,name,open,desc,rules,spec,mainId,usage,ledger, repo:{url,branch,token}, cycle:{version,branch,started}, conflict_policy, conflicts[], agents[], tasks[], bugs[], modules[], log[], commits[], releases[], mrs[], releasing}`
- **Instructions « annule et remplace »** : `p.instructions[{id,n,d,by,scope,text,active,key?,replaced_by?}]` ne s'écrivent que via `rights.add_instruction(pp, ins, replaces)` : elle désactive (`active:false`) les instructions dont le n° est dans `replaces` et toute instruction active de même `key` (réponse à une décision structurante : `key="dec:"+question`, donc une même question reposée remplace l'ancienne réponse). Action agent `instruction{text,scope,replaces[]}` et job `instr_add{scope,text,replaces[]}` ; le n° est affiché dans l'IHM et dans les prompts (`- n°12 …`). Seules les 30 dernières instructions remplacées sont conservées. **Consolidation** (bouton « Consolider », job `instr_consolidate`, `engine.instr_consolidate`) : un agent API sans mémoire reçoit toutes les instructions actives et répond par l'action `instr_rewrite{items[{text,scope,replaces[]}],obsolete[]}` (acceptée uniquement si `p.instr_consol.analyzing` = son id) ; les instructions remplacées/obsolètes sont désactivées, la liste est journalisée. Dans l'analyse de cohérence, entre deux instructions contradictoires la plus récente (n° le plus élevé) l'emporte ; `prules.dump` affiche la règle des conflits avec le nom de l'agent désigné (et non son id).
- Agent : `{id,name,service,role,branch,canBug,talk[ids ; vide = tous, ["none"] = personne],notes,history[],state,work}` — **dépôt et token au niveau projet**, seule la **branche** varie par agent (peut être partagée).
- Tâche : `{id,parent,title,desc,who,status("à faire|en cours|terminée"),modules[],result,running,retry_at}`. Bug : `{id,t,d,sev,status,modules[],by}`. Module : `{id,name,desc}`.
- `log[]` : `{d,from,to,text}` = historique de **toutes** les discussions (Vous, agents, « Système », « Application »).
- **Coûts** : `ai.call_ai` renvoie un `Reply(str)` avec `.usage={in,out}` (Anthropic : `input_tokens`+cache, `output_tokens` ; OpenAI : `prompt_tokens`, `completion_tokens`). `engine.record_usage` cumule `{calls,in,out,cached,cost}` (`in` = total entrée **y compris** le cache ; `cached` = tokens lus dans le cache ; coût : lecture de cache à 10 % du tarif d'entrée, écriture à 125 %) dans `agent.usage` et `p.usage` (le total survit à la révocation d'un agent) et ajoute une ligne à `p.ledger` (300 max). Coût = tokens × tarifs du service (`service.pin` / `service.pout`, **$ par million de tokens, saisis par l'utilisateur**, jamais préremplis car les tarifs changent). Écrit par le serveur uniquement : **le front n'ajoute pas de valeur par défaut à `usage`/`ledger`** (sinon la fusion à trois voies écraserait les compteurs). Job `reset_usage`. Les agents en chat manuel ne sont pas mesurés.
- `ensure(p)` (front) complète les anciens états : **y ajouter tout nouveau champ**.

## Blockers fantômes (MR) — complément
- **MR introuvable sur GitHub** (`pr_state` = `missing` : token sans accès au dépôt, numéro invalide) : `sync_mrs` ne conclut rien, mais compte les vérifications (`m["missing_n"]`) ; à `MISSING_WARN` (3) il avertit **une seule fois** l'utilisateur (`m["missing_warned"]`, ligne du journal) et `diagnose` / `get_blockers` ajoutent « introuvable sur GitHub : vérifiez le token… ou marquez-la terminée ». Les compteurs sont remis à zéro si la MR redevient visible (`open`). Le bouton « Marquer terminée » reste le secours.

## Interruptions et reprise des tâches (`engine.py`)
- **Pourquoi un agent « oubliait » ou ne reprenait pas** : l'historique envoyé à l'IA est borné (30 derniers messages, abrégé, compacté en cas de dépassement) et la consigne d'une tâche n'était que dans le message de départ de `run_task` ; une sollicitation (dialogue, étape de workflow, suivi, autre agent) pouvait faire sortir ce message du contexte, et seule la reprise après quota relançait une tâche.
- **Rappel permanent** : `focus_text(p, a)` ajoute au bloc **changeant** du prompt système la section « Ta tâche en cours » (id, titre, **consigne d'origine**, modules, dernier compte rendu, interruption éventuelle), reconstruite à chaque tour depuis l'état : elle ne dépend plus de l'historique. Ne jamais la mettre dans les blocs mis en cache. La règle d'équipe « une interruption ne remplace pas ta tâche » est dans `RULES`.
- **Marquage** : `ask(...)` appelle `mark_interrupted` quand l'appelant n'est pas « Application » (hors `fresh`) et que l'agent a une tâche `en cours` → `t["interrupted"] = {by, d, ts}`.
- **Reprise dans la boucle** : `run_task` détecte `interrupted` après chaque tour, l'efface, et renvoie `resume_text` (consigne d'origine incluse) à la place du simple `NUDGE` ; le retour d'actions non traité est conservé et ce tour ne compte pas comme « sans action ».
- **Reprise hors boucle** : `resume_interrupted(u, pid)` (fin de `say`, fin d'étape de workflow, chaque passage du suivi `_tick`) relance `run_task` pour toute tâche `resumable` : interrompue, non lancée, agent libre, statut `en cours` ou `en attente` (repassée « à faire »), **sauf** décision en attente sur la tâche, `blocked`, `stopped` (arrêt par l'utilisateur/l'agent principal), `fail`, `retry_at`, conflit ouvert, dépendances non satisfaites, agent manuel, ou `autopilot` = `off`. Bornée par `MAX_RESUME` (3, compteur `t["resume_n"]`, remis à zéro à la clôture). Chaque reprise est journalisée (« reprise automatique (n/3) »).
- Tests : classe `Interruptions` dans `tests/test_engine.py`.

## Gros fichiers (`engine.py`, `ai.py`)
- **Cause des fichiers « abrégés » et des relectures en boucle** : `shrink_history` réduisait à 400 caractères tout ancien retour d'actions sauf les 2 derniers messages ; lire 3 fichiers en abrégeait un, que l'agent relisait, ce qui en abrégeait un autre, etc. **Corrigé** : `shrink_history` garde désormais intacts les retours qui tiennent dans `HIST_BUDGET` (36 000 caractères, du plus récent au plus ancien) et abrège d'office un retour dont tous les fichiers (en-têtes « Fichier … ») ont été relus depuis ; en plus, `file_act` compte les relectures identiques d'un extrait par un agent (`READS`) et, dès la 3e sans écriture entre-temps, ajoute un avertissement (« passe à edit_file… ») ; une écriture réussie remet le compteur à zéro. Ancien comportement, pour mémoire : tout ancien retour d'actions était réduit à 400 caractères (sauf les 2 derniers messages). Un fichier lu puis réécrit quelques tours plus tard n'est donc plus dans le contexte de l'agent, et un `write_file` (qui remplace le fichier ENTIER) à partir de ce texte abrégé le tronque. Découper le fichier en parties lues une à une ne change rien : chaque partie est abrégée à son tour.
- **Lecture** : `read_view(t, x)` (3 espaces de travail : GitHub, répertoire local, worktree git) → `read_file` accepte `from_line`/`to_line` (lignes, 1-based) ou `offset`/`limit` (caractères) ; au plus `READ_MAX` (12 000) caractères ; le retour dit comment lire la suite.
- **`edit_file{path,edits:[{old,new,all?}],message}`** (`edit_act`) : remplacements de texte, tout ou rien ; chaque `old` doit être unique (sinon refus avec le nombre d'occurrences, ou `all:true`) ; fins de ligne `\r\n` des fichiers Windows respectées ; passe par `repo_act`/`write_file` donc **mêmes verrous, mêmes droits, même commit** que `write_file` dans chaque mode. En **répertoire local**, `locked_rmw` tient le verrou du fichier pendant TOUTE l'opération (lecture + écriture ; verrou pris ici puis rendu, ou verrou déjà tenu conservé) : personne ne peut modifier le fichier entre les deux ; même chose pour la lecture du garde-fou de `write_file`. Worktree git (un agent par branche) et GitHub : pas de verrou.
- **`write_chunk{path,index,total,content,message?,sha256?}`** (`chunk_act`) : morceaux numérotés (≤ 50, dans le désordre), gardés en mémoire (`CHUNK_BUF`, par utilisateur/projet/agent/chemin, purge après `CHUNK_TTL` = 30 min, perdus au redémarrage) ; au dernier morceau l'application reconstitue, vérifie `sha256` si fourni, écrit comme `write_file` et renvoie taille et empreinte. Rien n'est écrit tant qu'il manque un morceau.
- **Garde-fou** (`file_act`) : `write_file` est refusé si le fichier existant fait ≥ 2 000 caractères et que le nouveau contenu en fait moins de la moitié (`SHRINK_GUARD`) ; l'agent doit utiliser `edit_file`/`write_chunk` ou ajouter `confirm_shrink:true`. Une lecture supplémentaire par écriture (`raw_read`, drapeau interne `_raw` retiré des actions de l'agent).
- **Réseau** (`ai._post`) : `RemoteDisconnected`, reset, délai dépassé ou hôte injoignable → 2 nouvelles tentatives (2 s puis 6 s) avant une erreur 502 explicite ; les erreurs HTTP (quota…) ne sont pas rejouées. Avant, `RemoteDisconnected` n'était pas intercepté et faisait échouer la tâche (« Erreur interne »).
- Tests : `tests/test_fichiers.py`.

## Économie de tokens (`engine.py` + `ai.py`)
- `sys_prompt` renvoie un `ai.System` en **3 blocs, du plus stable au plus changeant** : (1) commun à tous les agents : règles par défaut **verrouillées** (`rulebook.locked_core()`), `ACTIONS`, règles du projet, description, modules, spécifications ; (2) propre à l'agent mais rarement modifié : règles d'agent, workflows, instructions, « Toi », droits, dépôt, équipe ; (3) change presque à chaque tour : nouveautés, travail des autres, tâches, bugs, décisions, notes. Les blocs 1 et 2 sont mis en cache (5 min) côté Anthropic. **Ne rien mettre de changeant dans les blocs 1 et 2** (sinon le cache est perdu) ; tout nouvel élément du prompt va dans le bloc qui correspond à sa fréquence de changement.
- `shrink_history` : dans l'historique envoyé à l'IA, les anciens retours d'actions (`[Application] Résultats de tes actions…`, ex. contenu de fichiers) sont abrégés à 400 caractères, sauf les 2 derniers messages. L'historique stocké n'est pas modifié.
- **Diff fourni aux validateurs** (`diff_text(rp, base, head, budget, per_file)`) : `review_mr` (15 000 car. max) et `review_task` (12 000 ; diff de la MR liée à la tâche, sinon de la branche de l'agent par rapport à la branche de travail — il peut inclure d'autres tâches) placent le diff (`compare` GitHub, champ `patch`) dans leur message : le validateur n'a plus à relire les fichiers un par un avec `read_file`. Tronqué par fichier (3 000 car.) et au total ; les binaires, fichiers trop gros ou hors budget sont listés pour une lecture à la demande. Aucun diff (agent en répertoire local, GitHub injoignable) → ancien comportement (consigne de lire avec `read_file`).
- Suite possible : lecture de fichier par plage de lignes, modèle économique pour le suivi/les validations, analyse des règles à la demande, `max_tokens` par type d'appel (`call_ai` l'accepte déjà).

## Moteur d'agents (`engine.py`)
- `ask(u,pid,aid,text,frm,depth)` : boucle d'au plus `MAX_STEPS`=6 tours : prompt système (`sys_prompt`, reconstruit à chaque tour depuis l'état frais) + historique (30 derniers messages) → `call_ai` → blocs ```` ```action {json} ``` ```` (`parse_acts` → `(texte, actions, erreurs)` : **aucun bloc ne se perd en silence** — JSON illisible, bloc non refermé (réponse tronquée) ou élément non objet produisent une erreur **renvoyée à l'agent** au tour suivant ; un bloc peut contenir une liste d'actions) → `do_act` (toute exception inattendue devient un refus « erreur interne » renvoyé à l'agent, trace en console). Les **retours** (lecture de fichier, liste, réponse d'un autre agent, refus/erreurs) sont renvoyés à l'agent au tour suivant ; les écritures réussies sont seulement journalisées.
- Actions : `list_files`, `read_file` (plage `from_line`/`to_line` ou `offset`/`limit`), `write_file`, `edit_file`, `write_chunk`, `delete_file` (sur **la branche de l'agent** ; jamais sur la branche de base ; chemins validés par `safe_path`, `.github/`, `.git/` et `.agents/` interdits en écriture ; lecture tronquée à 12 000 car., écriture ≤ 200 000 car.), `message` (agents joignables ; le principal joint tous ; profondeur max 3 ; la réponse revient à l'expéditeur), `context`, `task_status`, `task`, `module`, `bug`, `bug_fix`, `bug_status`, `link_modules`, `ask_user`, `instruction`, `spec`, `get_progress` (voir « Droits, décisions et instructions »).
- **Toute nouvelle règle par défaut se déclare dans `rulebook.py` (`CORE` ou `MODULES`, avec un sujet) et toute nouvelle action dans `ACTIONS`** (elles alimentent le prompt système ET le fichier `.agents/<Prénom>.md`). `engine.RULES` n'est plus qu'une vue à plat de toutes les règles par défaut (`rulebook.all_lines()`), utilisée par l'analyse de cohérence.
- Onboarding/synchronisation (`provision`) : crée la branche de l'agent si absente et pousse `.agents/<Prénom>.md` (règles équipe + projet, rôle, droits, actions, notes).
- Tâches (`run_task`) : quota 429/529 → agent `suspendu`, `retry_at`, reprise automatique par `threading.Timer` ; `recover()` au démarrage remet les compteurs à zéro, marque les tâches interrompues et replanifie les reprises.
- **Release et intégration** : voir « Workflow git » ci-dessous.
- Agent principal (`mainId`) : dialogue via le prompt de la Vue globale ; écrit à tous, crée les tâches, tient les spécifications, réalise MR + tag.

## Droits, décisions et instructions (`rights.py` + `engine.py`)
- **Précision jointe à une option** : `decide(decision:"answer")` reçoit `answer` (l'option cliquée, comparée telle quelle aux `options`) et `note` (texte du champ libre de la carte). `note` n'est prise en compte que si `answer` est une option ; la réponse enregistrée, journalisée et transmise à l'agent est « option — précision de l'utilisateur : … » (`full`) ; pour les validations (tâche, MR, escalade) la précision sert de motif/consigne. Le front exige la précision quand le libellé de l'option contient « précis ».
- **Décisions redondantes** : toute décision passe par `add_decision(pp, d, replaces=())` (jamais d'`append` direct). Les décisions `attente` plus anciennes qui portent sur le même sujet passent à `remplacée` (`replaced_by`, note « Remplacée par la décision n° N ») : même clé (`conflict`, `mr_review`, `wf_run`, `review`, `escalation`+tâche, proposition de même type et titre), question très proche (mots ≥ 4 lettres, Jaccard ≥ 0,5 ; ≥ 0,3 si même tâche), ou numéros listés dans `replaces` de l'action `ask_user`. La tâche bloquée par l'ancienne est libérée (ou rebloquée par la nouvelle).
- **Capacités** (`rights.CAPS`) : `subtask, task_top, module, bug, bug_update, bug_verify, mr_review, link`, chacune `free | approve | no` (`mr_review` = « valider les merge requests » : seulement `free` ou `no`, repli sur `bug_verify` pour les rôles créés avant ce droit ; défaut `free` pour Chef de projet, Architecte, Testeur QA ; l'agent principal l'a toujours). Définies par **rôle** (`role.caps`, éditables dans la vue globale Rôles ; repli sur `DEFAULT_CAPS` par nom de rôle standard — **à garder synchronisé avec `DEF_CAPS` de `static/index.html`**), surchargeables par agent (`agent.caps`, **sans interface pour l'instant**). `rights.level()` applique ensuite : le principal ne peut pas être en dessous de `approve` pour `task_top`/`module` ; `agent.canBug` (ancien drapeau) réactive `bug` ; **autonomie du projet** `p.autonomy` : `prudent` (tout `free` de création → `approve`), `balanced`, `auto` (`approve` → `free` pour tâches de 1er niveau et modules).
- **Sous-tâches** : libres sous une tâche dont l'agent est responsable ou qu'il a créée (`rights.owns`), partout pour le principal ; profondeur max 4 ; doublons de titre refusés ; max `MAX_CREATE`=8 créations par échange.
- **Propositions** : un niveau `approve` ne crée rien : `engine.propose` ajoute une entrée à `p.decisions` (`kind: task|module|bug|question`, `status: attente|acceptée|refusée|répondue`, `payload`, `why`). Le navigateur **ne modifie jamais** `decisions` : il envoie le job `decide`, qui crée l'élément (`rights.create_from`, champs titre/nom/description modifiables) ou renvoie le refus/la réponse à l'agent par un `ask`.
- **Questions** (`ask_user`) : la tâche liée passe « en attente » (`task.blocked`) ; la réponse la remet « en cours », est transmise à l'agent, et si `structural` s'ajoute à `p.instructions`.
- **Bugs** : statuts `ouvert → en correction → corrigé → vérifié | rouvert` (`résolu` = ancien statut, traité comme fermé). Un bug crée (si absent) la tâche système « Corrections : <module> » (ou « Corrections (global) ») sans validation ; `bug_fix` y ajoute des sous-tâches (`task.bug`) ; quand toutes sont terminées via `task_status`/`run_task`, le bug passe à « corrigé » (`rights.on_task_done`). **Un changement de statut fait à la main dans l'interface ne déclenche pas cette mise à jour.**
- **Instructions partagées** : `p.instructions` (`{id,n,d,by,scope,text,active}`, portée `global | role:<nom> | agent:<prénom> | module:<nom>`), écrites par l'agent principal (action `instruction`) ou l'utilisateur (job `instr_add`) ; injectées dans le prompt de chaque agent concerné avec un bloc « Nouveautés » basé sur `p.seq` / `agent.seen_seq`. Les spécifications (`p.spec`, `p.spec_n`) sont aussi dans le prompt de **tous** les agents (6000 car. max).
- `get_progress` répond depuis l'état, **sans appel IA**. **Plafond de budget** : `p.budget` (client) ; `engine.check_budget` refuse tout appel API (erreur 402) quand `p.usage.cost` l'atteint.
- Écrits **uniquement par le serveur** (le front ne les modifie pas, et n'ajoute pas de valeur par défaut) : `decisions, instructions, seq, spec_n`, `agent.seen_seq`. Côté client : `autonomy`, `budget`, `role.caps`.

## Règles par défaut, sujets et priorité (`rulebook.py` + `rights.py` + `engine.py`)
Voir `docs/PROPOSITION-HARMONISATION-REGLES.md` (décisions du 24 nov. 2026 : option 1, pas de règles propres aux rôles/modules, question à la saisie, la release est publiée par l'utilisateur).
- **Règles par défaut** (`rulebook.py`) : socle commun (`CORE`, ~15 règles, chacune avec un **sujet**) + un **module par mode** (`MODULES` : `github`, `local`, `git`, choisi par `engine.agent_mode`). Les règles **verrouillées** (`locked`) décrivent des garde-fous du code (droits, vérification des tâches, verrous, `.github/`/`.agents/`, release par l'utilisateur…) : aucune règle utilisateur ne les remplace. ~520 à 600 tokens par agent au lieu de ~1 680.
- **Placement dans le prompt** : règles verrouillées dans le bloc 1 (partagé, mis en cache : **identique pour tous les agents**) ; règles modifiables non remplacées + module du mode dans le bloc 2 (propre à l'agent, `parts[20]`). Ne jamais mettre dans le bloc 1 une règle qui dépend de l'agent.
- **Sujets modifiables** (`rulebook.SUBJECTS`, dupliqués dans `static/index.html`, constante `SUBJ`, test de synchronisation) : `langue, ambiguite, interruption, coordination, fichier_contexte, fichiers`. Une instruction peut porter un `subject` (formulaire « Nouvelle instruction », ou champ `subject` de l'action `instruction`) ; `rights.clean_subject` ignore tout autre sujet.
- **Priorité** (`rights.subject_winners`) : pour un agent et un sujet, la portée la plus spécifique l'emporte (`agent` > `role`/`module` > `global`, `rights.scope_rank`), puis la plus récente ; la règle par défaut du même sujet n'est alors plus envoyée (`rights.overridden_subjects`) et `instruction_lines` n'affiche que l'instruction gagnante. Les règles en texte (`p.rules`, `agent.rules`) sont découpées par `rulebook.parse_rules` (une règle par ligne ou puce ; une règle qui commence par `[sujet]`, ex. `- [langue] Réponds en anglais`, porte ce sujet). **Aucune migration** : le texte reste stocké tel quel et édité dans les mêmes fenêtres ; un texte sans `[sujet]` part inchangé dans le prompt. Les règles à sujet quittent le bloc partagé : `prules.shared_rules_text` (projet, sans les règles à sujet) / `prules.agent_rules_text` (sans les règles à sujet) / `prules.subject_rules_text` (`parts[21]`, bloc propre à l'agent : seules les règles à sujet **gagnantes** pour cet agent). Les règles en texte n'ont pas de date : elles sont plus anciennes que toute instruction du même niveau ; un agent > rôle/module > global reste valable (`rights.rule_candidates`, `subject_winners`).
- **Plus récent remplace** : `rights.add_instruction` désactive aussi l'instruction active de même `subject` **et** de même portée.
- **Question à la saisie** (`engine.rule_submit`, utilisée par le job `instr_add` et l'action `instruction`) : si la nouvelle instruction est plus large que, de même sujet qu'une instruction active **ou qu'une règle en texte d'un agent** plus spécifique et visant aussi les mêmes agents (`rights.rule_conflicts`), elle n'est **pas** enregistrée : une décision `question` (champ `ruleconf`) propose « remplacer / garder la spécifique / sujets différents ». La réponse est appliquée dans `decide` (« remplacer » retire aussi la règle en texte de l'agent de ses règles) ; aucun message n'est envoyé à l'agent. Un texte de règles modifié à la main n'ouvre pas de question : le contrôle de cohérence (`prules.lint`) signale, en niveau info, la règle qui l'emporte sur les autres pour chaque agent. Plus spécifique que l'existant : enregistrée d'office.
- **Actions filtrées** : `ACTION_LINES` (toutes les actions) → `engine.action_applies(p, a, nom)` selon le mode (github/local/git), les droits (`rights.level`), l'agent principal, les agents joignables et les workflows actifs. Les actions de `ACTIONS_ALWAYS` (fichiers, `get_blockers`, `context`, `task_status`, `ask_user`) sont dans le bloc partagé (`actions_common`) ; les autres dans le bloc propre à l'agent (`actions_extra`, `parts[22]`) ; le fichier de contexte reçoit `actions_text`. `instr_rewrite` n'apparaît jamais dans le prompt courant (elle est décrite dans la demande de consolidation, qui garde désormais le `subject`). Une action non proposée reste traitée par le code, qui la refuse avec un motif. **Toute nouvelle action** : l'ajouter à `ACTION_LINES` et la classer dans `ACTIONS_ALWAYS` ou dans `action_applies` (un test vérifie la liste). Gain : 33 à 50 % de la liste des actions selon le mode.
- **Analyse de cohérence par IA ciblée** (`engine.rules_analysis`, `prules.dump`) : l'IA ne voit que ce que le code ne tranche pas. Les règles à sujet sont arbitrées par `rights.subject_winners` et listées dans une section « Sujets tranchés AUTOMATIQUEMENT… (ne les signale pas) » ; seules les règles sans sujet, les instructions sans sujet et les workflows sont soumis. Règles intégrées : `analysis_builtin` (modules des modes utilisés seulement, sujets remplacés pour tous les agents exclus). Rien à analyser (`prules.has_material`) → aucun appel. Même texte que la dernière analyse (`rules_report.ai_hash`) → aucun appel, sauf `force` (bouton « contrôle de cohérence », `rules_check`).
- **Droits par défaut : source unique** `rights.DEFAULT_CAPS` / `rights.BASE_CAPS`, servis par `GET /api/state` (`defcaps`, `defbase`) ; `index.html` n'en garde plus de copie (`DEFCAPS`/`DEFBASE`, `defCaps()`).

## Règles du projet et workflows (`project_rules.py` + `engine.py`)
- **Données** (modifiées par le navigateur) : `p.rules` (règles globales), `agent.rules` (règles d'un agent), `p.workflows[{id,name,desc,enabled,allow_agent,schedule:{mode: off|daily|interval, time:"HH:MM", days:[0-6, lundi=0], every}, steps:[{id, kind: ask|start_tasks|ask_user, who: principal|assignee|requester|agent:<id>|role:<id>, text, on_ko: stop|continue|ask_user|goto, goto}]}]`. **Écrites par le serveur uniquement** : `wf_runs`, `wf_state` (dernier déclenchement de chaque minuterie), `rules_snap`, `rules_log`, `rules_report{static, ai, ai_ts, ai_note, analyzing, ts}`, `agent.wf_ctx`.
- **Communication des modifications** : après toute modification de règles ou de workflows, le navigateur envoie le job `rules_changed` (il passe par `job()`, qui sauvegarde l'état d'abord). `rules_changed` compare l'état à `rules_snap` (`prules.diff`), ajoute des entrées à `rules_log` (séquence `n`), journalise un message « Règles mises à jour » pour chaque agent **concerné** (`prules.concerned` : règles globales et workflows → tous ; règles d'un agent → lui seul), republie leur fichier de contexte (`provision`) et relance l'analyse de cohérence. Les agents reçoivent aussi un bloc « Nouveautés » dans leur prompt (`prules.news_lines`, mécanisme `seen_seq`). Prompt et `ctx_text` contiennent les règles de l'agent et la description des workflows actifs (`agent_rules_text`, `workflows_text`, 10 max).
- **Exécution** : `workflow_start` (refuse un doublon sur la même tâche et plus de `WF_MAX_PER_HOUR`=10 déroulements/heure ; lance `wf_continue` en arrière-plan) → `wf_continue` exécute les étapes (au plus `WF_MAX_STEPS`=20 étapes exécutées : garde-fou contre les boucles `goto`). Étape `ask` : `wf_do_step` envoie à l'acteur (`prules.resolve_actor`) la consigne, la tâche cible, le compte rendu des étapes précédentes ; l'agent conclut par l'action `wf_step {outcome ok|ko, comment}` (relancé une fois s'il oublie ; sinon `ok` « sans verdict explicite »). Étape `start_tasks` : `dispatch(force=True)` (même si le lancement automatique est désactivé). Étape `ask_user` : décision (`wf_run`, `wf_step`, `wf_after`) qui met le déroulement en pause (`run.waiting`) ; `decide` le reprend. `wf_after` applique `on_ko` (arrêt, suite, saut, ou question à l'utilisateur avec options continuer / relancer l'étape / arrêter). Un échec technique (`Err`) → `échoué` ; `wf_resume` repart de l'étape interrompue.
- **Déclencheurs** : utilisateur (job `workflow_run`, tâche cible facultative), agent (action `run_workflow`, si `enabled` et `allow_agent`), minuterie (`wf_timers`, appelé par `tick` **indépendamment du suivi** ; `prules.due` : quotidien à HH:MM sur certains jours, rattrapage limité à `WF_LATE`=6 h ; intervalle : la première observation démarre le compte à rebours sans lancer).
- **Cohérence** : `prules.lint` (déterministe : workflows sans nom/étape, doublons, heure invalide, intervalle trop court, minuterie sur workflow désactivé, acteur introuvable ou sans tâche cible en minuterie, acteur en chat manuel, sauts invalides, boucles, règle de conflit sur agent supprimé, aucun agent principal…) + `rules_analysis` (un agent API, le principal en priorité, reçoit `prules.dump` — règles intégrées, globales, par agent, workflows, réglages — et répond par l'action `rules_report`, acceptée **uniquement** si `rules_report.analyzing` vaut son identifiant). Résultat dans `rules_report`, affiché en tête de l'onglet Règles. **L'analyse est sans mémoire** (`ask(..., fresh=True)` : l'historique de l'agent n'est ni lu ni écrit, sinon d'anciennes versions des règles et d'anciens rapports polluent le contexte et le rapport « grossit ») ; `prules.dump` inclut les **instructions et décisions actives** de l'utilisateur (plus récentes que les règles : un point qu'elles précisent n'est plus ambigu).
- **Tests** : classe `Regles` de `tests/test_engine.py` ; patcher `engine.spawn` et, pour les minuteries, `engine.datetime`.

## Déblocage, réinitialisation et diagnostic (`engine.py`)
- **Pas d'« environnement d'exécution » d'agent** : un agent n'est qu'un historique de conversation (`agent.history`), des notes, une branche GitHub et des tâches ; tout passe par l'API GitHub, il n'existe aucun `.git` local ni état `MERGE_HEAD`. Un agent qui prétend le contraire hallucine une cause (cas réel : conflit resté ouvert → refus « conflit déjà en cours » → cause inventée → question absurde à l'utilisateur). Contre-mesures : règle explicite dans `RULES`, messages de refus factuels (`describe_conflict`), action `get_blockers`.
- **Conflits obsolètes** : `reconcile_conflicts` revérifie les conflits actifs (`OPEN_CONFLICT` = ouvert/escalade/pause) — plus aucun fichier en conflit **et** fusion réussie → clos (`close_conflict`/`_close_in` : statut, questions liées, tâche en attente), puis `after_conflict`. Appelé par `_tick` (toutes les `RECONCILE_EVERY`=300 s par conflit), avant tout refus dans `run_task` et `submit_mr` (`force`), et implicitement par un `pull` réussi. Un `pull` n'enregistre pas un second conflit si un est déjà actif.
- **Actions de l'utilisateur** (job `conflict_action{conflictId, action}`) : `check` (revérifier), `resolved` (déclarer résolu → suite), `retry` (relancer la résolution : résolveur de la règle, sinon agent principal), `abandon` (l'agent n'est plus bloqué ; un conflit persistant sera signalé de nouveau).
- **Réinitialiser un agent** (job `agent_reset{agentId, history, notes, branch, onboard}` → `agent_reset`) : annule ses attentes manuelles (`WAIT`), remet `work/state/seen_seq` à zéro, remet ses tâches en cours « à faire », clôt ses conflits (`abandonné`) et, avec `branch`, **remet sa branche sur la branche de travail** (`Repo.reset_branch`, force ; MR ouvertes → `annulée`), puis rejoue l'onboarding. Un appel IA déjà parti n'est pas interrompu (limite connue).
- **Diagnostic factuel** : `diagnose(p)` (sans IA) → `[{who, level: bloquant|attente|info, text, conflict?}]` ; exposé par `GET /api/diagnostic?project=` (bouton *Diagnostic des blocages* de l'onglet Équipe) et par l'action d'agent `get_blockers`. Tolérant aux états incomplets.
- **Décision « classer sans suite »** : `decide(..., "dismiss")` → statut `ignorée`, tâche liée débloquée.

## Autonomie : lancement automatique, tâches persistantes, reprise (`engine.py`)
Cause des « agents qui s'arrêtent » corrigée ici : avant, rien ne lançait les tâches, un tour d'agent s'arrêtait dès qu'une réponse n'avait pas d'action (ou après 6 étapes), la tâche passait alors d'office « à vérifier », et une exception laissait `running=True` pour toujours.
- **Lancement automatique** (`dispatch`, appelé par `tick` toutes les `APM_SUPERVISE_SECONDS`=60 s, et aussitôt après un événement via `spawn(tick)` : tâche créée, tâche vérifiée, MR fusionnée, job `decide`/`mr_retry`/`cycle_start`/`instr_add`) : une tâche `à faire` assignée démarre seule si ses dépendances sont satisfaites, si l'agent est libre (une tâche à la fois par agent), s'il n'est pas en chat manuel, sans conflit ouvert, sans échec en attente, sans enfants (tâche parente), budget non atteint. Réglage par projet : `p.autopilot = "off"`. Garde-fou `MAX_AUTO`=8 lancements par tâche, puis escalade à l'utilisateur (`auto_n`, `auto_escalated`). `tick` est protégé contre la réentrance (`TICKING`).
- **Tâche persistante** (`run_task`) : jusqu'à `MAX_ROUNDS`=6 tours de `MAX_ROUND_STEPS`=8 étapes. Après chaque tour, si la tâche est encore `en cours` : étapes épuisées (`stats["pending"]`) → on renvoie le retour non traité ; actions exécutées sans conclusion → `NUDGE` (« conclus avec task_status à vérifier, ou continue, ou demande ») ; deux tours consécutifs sans action → le travail est considéré rendu (`à vérifier`). Tours épuisés en plein travail → `à faire` + `resume` (relancée par le pilote avec « reprends là où tu t'es arrêté »). `ask(..., stats=, relog=, max_steps=)` renseigne `stats = {actions, pending}`.
- **Erreurs** : `quota`/`temp` → relances automatiques (`backoff`) ; `other` → `MAX_OTHER`=2 nouvelles tentatives avant `fail` ; `internal` (exception inattendue, interceptée par `run_task`) → `fail` + escalade directe. Exécution « fantôme » (`running` sans agent actif depuis `STALE_RUNNING`=15 min) réinitialisée par `_tick`. Contexte trop long (`_overflow`) → historique de l'agent compacté (4 derniers messages tronqués à 1500 car.) et nouvel essai. L'historique stocke les réponses tronquées à 6000 car. `say` (conversation) est relancé automatiquement après quota/erreur temporaire (`relog=False` : le message n'est pas journalisé deux fois).
- **Coordination entre agents** : `can_talk` — **par défaut un agent peut écrire à tous** (`talk` vide) ; `["none"]` = personne ; une liste = ces agents. Le prompt contient « Travail des autres agents » (`teamwork_text` : qui fait quoi, dépendances) ; le message de démarrage d'une tâche contient le contexte des **dépendances** (`dep_context` : compte rendu et branche des tâches dont elle dépend) et une consigne de coordination (`coordination_hint`) ; `RULES` impose l'initiative de coordination et la persistance après erreur.

## Workflow git : branche de travail par release (`engine.py` + `github.py`)
- **La branche principale (`repo.branch`) est réservée à la release finale.** Chaque release a une **branche de travail** `release/<version>` (`p.cycle`), créée depuis la principale par `cycle_start`. `Repo.work` = branche de travail du cycle, sinon la base ; `Repo.ensure_branch(b)` crée depuis `work`. Aucun agent n'écrit sur la base ni sur la branche de travail (`repo_act`, `provision`).
- **Pull** (`pull`) : fusion de la branche de travail dans la branche de l'agent (`POST /merges`) — automatique au démarrage de `run_task` et avant une MR, ou via l'action `pull`. États : `uptodate | merged | conflict | skip`.
- **Merge request** : `submit_mr` (action `merge_request`, ou automatique en fin de `run_task`) → pull, puis PR agent → branche de travail, enregistrée dans `p.mrs` (`{id,n,from,to,by,by_id,task,status: ouverte|fusionnée|conflit|refusée|annulée|terminée,note,checked,done}`) → `review_mr` (thread) : l'**agent principal** (ou un agent dont le rôle a le droit `mr_review`, jamais l'auteur ; `pick_mr_reviewer`) relit fichiers/commits et conclut par `mr_review approved|rejected` (`apply_mr_review` → `merge_mr`) ; pas de validateur possible → question à l'utilisateur (`decision.mr_review`). Refus : motif renvoyé à l'auteur.
- **« Blockers fantômes » : synchronisation des MR avec GitHub, sans IA** (`engine.sync_mrs`, `Repo.pr_state`). Une MR `ouverte|conflit` (`MR_ACTIVE`) dans l'application mais **fusionnée ou fermée dans le dépôt central** est retirée des blocages : `fusionnée` si GitHub dit « merged », `annulée` si fermée sans fusion (`note` « détectée automatiquement », message « Système → Vous » dans le journal). `_close_mr_in` libère aussi ce qui l'attendait : conflit lié (`résolu`, ou `abandonné` si annulée), question de validation `mr_review` (`répondue`), tâches dépendantes (`deps_unmet` ne les retient plus). Appelée par `tick` **avant** `_tick` et **même si `supervision` = off**, au plus toutes les `MR_SYNC_EVERY`=120 s par MR (`m.checked`) ; en `force=True` juste avant de **refuser** quelque chose à cause d'une MR : action `get_blockers`, `GET /api/diagnostic`, `run_task` (dépendances), `submit_mr` (MR déjà ouverte), `release`. Prudente : erreur réseau, dépôt/token absent ou MR introuvable (404 : accès ou numéro) → ne conclut rien (le bouton ci-dessous est le secours).
- **Secours manuel** (onglet Git → tableau des merge requests) : bouton **Marquer terminée** (job `mr_done`, avec confirmation) → statut `terminée`, **sans consulter GitHub**, mêmes libérations que ci-dessus ; bouton **Vérifier sur GitHub** (job `mr_sync`) = passage immédiat de `sync_mrs(force=True)`. Les deux déclenchent un `tick` ensuite. Une MR `terminée`/`annulée` n'est jamais rouverte par la synchronisation.
- **Dépendances** : `task.deps` (ids) ; `run_task` ne démarre pas tant que `deps_unmet` n'est pas vide (tâche non terminée **ou** MR de cette tâche encore `ouverte|conflit`) ; `task.waiting` l'indique ; `merge_mr` logue les tâches débloquées.
- **Conflits** (`open_conflict`, `p.conflicts`) : détectés par `Repo.conflict_info` (fichiers modifiés des deux côtés depuis l'ancêtre commun et différents). **Règle du projet `p.conflict_policy`** : `ask` (défaut : décision à l'utilisateur, options `CONFLICT_OPTS` : auteur / agent principal / pause), `author` (l'auteur de la branche résout), `agent:<id>` (agent désigné) ; un agent en chat manuel n'est jamais désigné automatiquement. Le résolveur reçoit base / sa version / version de la branche de travail et répond par `resolve_merge {conflict, files:[{path, content}]}` : `merge_with_resolution` crée un **commit de fusion à deux parents** sur la branche de l'auteur (arbre de l'auteur + changements de la branche de travail, fichiers en conflit remplacés). Résolution incomplète ou avec marqueurs → refusée et renvoyée à l'agent ; 2 échecs, conflit trop gros (> 8 fichiers ou 60 000 car.) ou résolveur injoignable → escalade à l'utilisateur. Après résolution (`after_conflict`) : MR fusionnée, soumission reprise, ou tâche relancée. Pause : l'utilisateur résout sur GitHub puis `mr_retry`.
- **Publication** (`release`) : exige un cycle actif et aucune MR `ouverte|conflit` ; PR branche de travail → base fusionnée, tag + release GitHub, `p.cycle` supprimé. Sans dépôt configuré : enregistrement local seulement.
- Limites : les modes de fichier (exécutable) ne sont pas conservés lors d'une résolution ; `compare` GitHub est limité à 300 fichiers ; une branche d'agent créée avant le cycle se met à jour par pull.
- **Tests** : `tests/test_engine.py` embarque un faux GitHub à historique de commits (ancêtre commun, fusion à trois voies, conflits) — la classe `Integration` couvre ce workflow.

## Vérification des tâches et suivi (`engine.py`)
- **Statuts de tâche** : `à faire, en cours, en attente, à vérifier, terminée`. **Une tâche n'est jamais « terminée » d'office** : en fin de `run_task`, ou sur `task_status terminée` d'un agent (converti), elle passe `à vérifier` ; seuls `task_review accepted` (agent principal, ou agent avec `bug_verify` libre, jamais l'assigné) ou l'utilisateur la clôturent. Une validation manuelle dans l'interface contourne la vérification.
- **Vérification** (`review_task`, thread) : réservation atomique (`task.reviewing`), prompt avec description, compte rendu et **preuves** (`evidence` : commits de l'agent depuis `task.started`, ou « aucune écriture ») ; le vérificateur relit les fichiers via `read_file` + `"agent":"<prénom>"` (lecture seule sur la branche d'un autre agent, ou `"base"`). `apply_review` : `accepted` → `terminée` (+ `on_task_done` des bugs) ; `rejected` (motif obligatoire) → `à faire` et relance de l'agent avec le motif ; au `MAX_REVIEWS`=3ᵉ refus → escalade à l'utilisateur. Vérificateur muet 2 fois, ou personne d'éligible (principal en chat manuel…) → question de validation à l'utilisateur (`decision.review`).
- **Échecs d'appel** (`classify`) : `quota` et `temp` (réseau, 5xx) → **relance automatique** (`backoff` : délai du fournisseur puis 5, 15, 30 min, puis **toutes les heures** ; `temp` abandonné après `MAX_TEMP`=6 essais ; `quota` sans limite), l'agent est « suspendu » ; `budget` (402), `auth`, `model` → **escalade directe** à l'utilisateur (l'agent principal n'y peut rien) ; `other` → `task.fail`.
- **Suivi** (`tick`, boucle `supervisor_loop`, désactivable par projet : `p.supervision = "off"`) : replanifie les reprises manquantes, déclenche les vérifications en attente, repère les tâches en échec (`fail`) ou **inactives** (`en cours` lancée par le moteur, sans activité depuis `STALL_SECONDS`=10 min) ; il **interroge l'agent principal** (message « [Suivi automatique] », un seul par passage, délai de carence `SUP_COOLDOWN`=10 min) qui peut interroger l'agent (`message`), le relancer (`relaunch`, max `MAX_RELAUNCH`=3) ou remonter via `ask_user` ; après 2 interventions sans succès, ou si le principal est en chat manuel, **escalade directe** : décision à l'utilisateur (`add_escalation` : relancer / pause / abandonner, `decision.escalation`).
- **Décisions** : répondre à une question liée à une tâche **relance automatiquement la tâche** (`run_task` avec la décision) ; l'agent n'a plus besoin d'être relancé à la main. Escalade : option 1 ou texte libre → relance (le texte devient la consigne), option 2 → `en attente`, option 3 → abandon (`terminée` + `abandoned`).
- Champs de tâche écrits **par le serveur uniquement** : `started, touched, retries, retry_at, fail, reviewing, reviews, review_note, reviewed, review_fail, review_asked, review_err, sup_n, sup_ts, relaunch_n, abandoned, blocked` ; projet : `sup_err_ts`. Côté client : `supervision`.
- **Tests** : toujours patcher `engine.spawn` (threads d'arrière-plan : vérifications, relances) et vider `engine.TIMERS`, sinon des threads fuient d'un test à l'autre.

## Modes de connexion d'un agent (`agent.mode`)
- `api` (défaut) : `ai.call_ai` avec la clé du service. `manual` : **chat manuel**, sans API : `engine.manual_exchange` publie un prompt dans `p.pending` (`{id,agent,name,service,full,short,new,d}`), le thread **attend** (`WAIT`, 24 h) que l'utilisateur colle la réponse du chatbot (`/api/manual/answer`) ; les actions de la réponse sont ensuite exécutées comme d'habitude (les retours de lecture arrivent dans un nouveau prompt). `full` = instructions complètes (nouvelle conversation), `short` = suite (`agent.session` mémorise qu'une conversation existe).
- **Décision : on n'automatise pas les sites de chat** (claude.ai, chatgpt.com…) : pas d'API publique pour les abonnements grand public, conditions d'utilisation contraires (Anthropic l'applique techniquement), fragile. Alternatives gratuites sans automatisation de site : API à offre gratuite (ex. Gemini via AI Studio, avec limites) ou modèle local compatible OpenAI (ex. Ollama : service `kind:"openai"`, URL `http://localhost:11434/v1`, clé factice).
- `p.pending` est écrit par le serveur uniquement ; `recover()` le vide au démarrage.

## Mode git local (`gitlocal.py` + `engine.py`) — étape 1 du chantier `docs/SPEC-git-local.md`

- **Réglage de projet `nogit`** (case « Sans git (verrous de fichiers) » dans la fenêtre du répertoire local) : absent ou `true` = comportement historique inchangé (verrous, aucun dépôt) ; `false` = mode git local. `git_mode(p)` = répertoire local défini **et** `nogit is False` ; `git_agent(p, a)` = agent local en mode git. **Désactivé par défaut** (tests `NonRegression`).
- **Dépôt** (`git_repo`) : contrôles préalables `gitlocal.preflight` puis `init`/clone/`recover`, une fois par (projet, dossier, remote) sous `GIT_LOCK` ; dossier inutilisable (non vide sans git avec remote, `origin` différent, modifications non commitées, merge inachevé…) → toutes les actions de l'agent sont refusées avec le motif, rien n'est écrit. `localdir_check` affiche le verdict (et revalide).
- **Espace de l'agent** (`git_workspace`) : un worktree `<localdir>/.myteam/worktrees/<prénom>`, créé au premier usage depuis la **cible** (`git_target` : branche de travail de la release en cours, sinon `develop`) ; branches de base/cible/`develop` interdites à l'agent ; une branche = un agent. **Stratégie de branches** (réglage de projet `branches`, fenêtre du répertoire local) : `task` (défaut, recommandée) = une branche `task/<prénom>/<id>-<titre>` par tâche en cours (`git_task_of`), le worktree change de branche au démarrage d'une nouvelle tâche (travail non commité enregistré en commit « WIP », ancienne branche supprimée si elle est fusionnée) et ne bouge pas quand la tâche passe à « à vérifier » ; sans tâche ni worktree : branche libre `task/<prénom>/libre`. **Branche héritée** : tant que l'ancienne branche de l'agent (`a["branch"]`) porte du travail non fusionné dans la cible (`unmerged`), il la garde ; une fois fusionnée il passe aux branches par tâche (l'ancienne n'est pas supprimée). `agent` = historique, une branche par agent (`a["branch"]`).
- **Actions** (`git_act`, aiguillées depuis `repo_act`/`do_act`) : `list_files`/`read_file`/`write_file`/`delete_file` sur **son worktree** (réutilise `locks.*` sur une copie du projet dont `localdir` = worktree : confinement, liens symboliques, `FORBIDDEN_WRITE` inchangés ; aucun verrou), puis `status`, `commit`, `diff` (contre la cible), `search`, `sync` (intègre `origin/<cible>` si le remote l'a, sinon la cible locale ; refusé si modifications non commitées ; conflit → marqueurs laissés à l'agent ; `{"abort":true}` pour renoncer), `git_log`, `git_show`. Aucune commande git libre, jamais de `push`/`checkout`/`reset`/`rebase` côté agent. `lock_file`/`pull`/`merge_request` renvoient un refus qui oriente vers `sync`.
- **Début de tâche** : `sync` programmatique (0 token), résultat injecté dans le message de tâche.
- **Fichier de contexte** : `<localdir>/.myteam/agents/<prénom>.md` (hors des branches, ignoré par git via `.git/info/exclude`) ; écrit par `provision` et l'action `context`.
- **Merge requests internes (étape 2)** : MR avec `git: true` (champs `from`, `to`, `n` séquentiel propre à l'application ; statuts inchangés : `ouverte`/`conflit` bloquent, `fusionnée`/`refusée`/`annulée`/`terminée`). `submit_mr` aiguille vers `git_submit` pour un agent en mode git : commit programmatique du reste, `sync` avec la cible (conflit → message à l'agent, rien soumis), puis MR + `review_mr` (le validateur reçoit `git_mr_view` = commits/fichiers/diff tronqué, et lit avec `git_show`). Fin de tâche (`à vérifier`) : soumission automatique. `merge_mr` aiguille vers `git_merge_mr` : alignement sur `origin/<cible>` (`update_target`), `integrate` (merge `--no-ff` dans le worktree d'intégration, sous `GIT_LOCK`), puis push de la branche de l'agent et de la cible (`push_target` : fetch + fusion + nouvel essai, jamais de force) ; remote injoignable = fusion locale conservée + avertissement. **Conflit à l'intégration** : MR `conflit`, auteur prévenu (sync → résolution → commit → `merge_request` : la même MR repart en validation), au-delà de 3 essais « intervention manuelle » (bouton Réessayer). `sync_mrs` déduit l'état **de git, sans IA ni réseau** (branche contenue dans la cible = `fusionnée`, branche supprimée = `annulée`) et coexiste avec les MR GitHub : fin des blockers fantômes pour ce mode.
- **Branche distante et poussée** : à la fusion, la branche de l'agent est poussée puis, pour une branche `task/…`, **supprimée sur le remote** sauf option `keepbranches` (« Conserver sur le remote les branches de tâche après fusion ») ; la branche locale est supprimée dès que son worktree la quitte. Une MR garde le dernier commit de sa branche (`tip`) : si la branche est supprimée après une fusion hors application, `sync_mrs` la déclare `fusionnée` (et non `annulée`). **Poussée à la demande** : bouton « Pousser les branches des agents » (onglet Git, mode git avec remote) = job `git_push` (`git_push(u, pid, aid=None)`).
- **Contrôles automatiques (`checks.py` + `engine.py`)** — tests/lint/build exécutés par l'application, **proposés par les agents, activés uniquement par l'utilisateur**. État de projet : `checks` (contrôles actifs : `id`, `name`, `command`, `when` = `validation`|`integration`|`both`, `blocking`, `timeout`, `retry_once`, `baseline` = `green`|`red`|`None`, `ver`), `check_history` (ajout/modification/retrait/restauration, avec l'ancienne version), `check_runs` (40 dernières exécutions), `check_tries` (échecs bloquants par branche).
  - **Proposition** : action `propose_check` (`name`, `command`, `when`, `blocking`, `explain` = explication SIMPLE non technique, obligatoire, `reason`) ; droit de rôle `check` (`rights.level` ne renvoie **jamais** `free` : proposition soumise ou interdit ; « Rédacteur technique » : interdit). `checks.analyze` calcule, **indépendamment de l'agent**, la vigilance (`faible`/`moyenne`/`élevée`) et **refuse d'office** sudo, téléchargement exécuté, `git push`/config globale, ssh/nc, suppression hors dossier, arrêt machine, PowerShell encodé… (refus renvoyé à l'agent, aucune carte). Même nom + autre commande = demande de modification ; une version révisée remplace la proposition en attente.
  - **Approbation** : carte « 🧪 Contrôle automatique » dans l'onglet Décisions (explication, ce qui change, vigilance, commande exacte repliée, confirmation renforcée si `élevée`) ; `decide(…, "accept")` active le **texte exact** (champs non modifiables), historise et lance `check_baseline` (exécution sur la cible : référence verte/rouge). Refus : motif renvoyé à l'agent. Toute modification redemande une approbation et remet la référence à zéro. L'utilisateur peut **Retirer** / **Restaurer** (job `check_remove`/`check_restore`, onglet Git).
  - **Exécution** (`run_checks`, `checks.run`) : à la soumission dans le worktree de l'agent (`git_submit`), et à l'intégration sur le **résultat de la fusion avant tout push** (`git_merge_mr`, sous `INTEGRATION_LOCK`). Un contrôle n'est **bloquant que s'il est déclaré bloquant ET de référence verte** (une réussite à l'intégration l'établit). Échec bloquant à la soumission : fin de la sortie renvoyée à l'agent (`CHECK_TRIES`=2 puis transmis au validateur avec avertissement) ; à l'intégration : `rollback` de la cible locale, MR `conflit` renvoyée à l'auteur (3 essais puis intervention manuelle). Une soumission refusée en fin de tâche renvoie la tâche à l'agent (`task_resubmit`, 3 fois puis question à l'utilisateur) au lieu de la faire vérifier. Le validateur voit le résumé (`checks_text`) ou « aucun contrôle configuré ». Garde-fous d'exécution : délai maximal (arbre de processus tué), sortie limitée (2 500 car.), environnement nettoyé (ni jeton ni clé), **une seule exécution à la fois** (`CHECK_LOCK`), rejouable une fois (`retry_once`).
- **Releases en mode git** (`git_cycle_start`, `git_release`, aiguillées depuis `cycle_start`/`release` quand `git_mode(p)`) : démarrer = `release/<version>` créée depuis `develop` (alignée sur le remote si possible) et poussée ; les MR git ouvertes visant `develop` sont redirigées vers la release ; `git_target` devient la release (les agents s'y synchronisent). Publier : refusée s'il reste une MR ouverte/en conflit, une tâche « à vérifier » ou si le tag existe ; sous `INTEGRATION_LOCK` : alignement sur le remote, fusion de la release dans la base (`main`), **contrôles d'intégration sur la base fusionnée** (échec bloquant = base remise comme avant, release toujours en cours), **tag annoté** (notes en message), `develop` avancée jusqu'à la base (avance rapide, sinon fusion ; conflit = avertissement, `develop` intacte), poussée de la base, du tag, de `develop` et de la release si un remote existe (échec = avertissement, release faite en local), release GitHub via l'API en best-effort, dépôt racine remis sur la base (`restore_root`). Une MR « Release finale » est ajoutée à l'historique. Après publication, la cible redevient `develop`.
- **Règle de conflit du projet en mode git** (`conflict_policy` : `ask` défaut | `author` | `agent:<id>`, réglée via « Conflits de fusion » de l'onglet Git) : un conflit d'intégration d'une MR git (`open_git_conflict`) crée une entrée de `conflicts` (`git: true`, `mr`, `mode` = `worktree`|`direct`|`manual`) comme en mode GitHub (même tableau, mêmes boutons Vérifier/Classer résolu/Relancer/Abandonner). `author` : l'auteur résout dans SON worktree (sync, résolution, commit) — le conflit est clos par sa **nouvelle soumission** (re-validation), `reconcile_conflicts` n'y touche pas ; `agent:<id>` ou choix « l'agent principal » : le résolveur reçoit les trois versions (base, cible, auteur) et répond par `resolve_merge`, la résolution est portée par la MR (`resolution`) et **appliquée par `git_merge_mr`** (`LocalGit.integrate(resolutions=…)`, vrai commit de fusion, contrôles d'intégration compris) ; `ask` : décision de l'utilisateur (`CONFLICT_OPTS`, « Je m'en occupe » = pause `manual`, levée par « Vérifier » quand `LocalGit.conflicts` — simulation de fusion qui ne modifie rien — ne trouve plus de conflit). Résolution incomplète ou avec marqueurs refusée ; 2 échecs du résolveur ou > 3 essais pour une MR : décision de l'utilisateur (`escalade`). Une MR close clôt son conflit.
- **Fin de chantier (22 nov. 2026)** : **annulation/arrêt d'un agent** (`git_stop_note`) : `cancel` écarte les modifications NON commitées de son worktree (`LocalGit.discard` : reset au dernier commit, fichiers non suivis supprimés, sync en conflit abandonnée ; ses commits restent), un simple arrêt les conserve (enregistrées en « WIP » au prochain changement de tâche) ; **branche héritée renommée** en branche de la tâche (`task/<prénom>/<id>-<titre>`) quand l'agent n'a qu'UNE tâche en cours et aucune MR ouverte sur cette branche (sinon elle est gardée jusqu'à sa fusion) ; **« Pousser main, develop et les tags »** (job `git_push_release`) : reprise de la poussée de la base, de `develop`, de la release en cours et des tags après un échec (réalignement sur le remote, jamais de force).
- **Limites connues du mode git local** : conflits à la synchronisation d'un agent non soumis à la règle du projet (l'agent les résout) ; contrôles automatiques et releases limités au mode git ; vigilance des commandes = analyse de texte (garde-fou) ; non testé sous Windows, avec GitHub réel (release via l'API en best-effort) ni avec de vrais agents IA (réponses simulées dans les tests).

## Répertoire local et verrous de fichiers (`locks.py` + `engine.py`)
- **Projet** : `p.localdir` (chemin absolu sur la machine du serveur, onglet Git & releases, bouton « Répertoire local » ; le job `localdir_check` vérifie l'accès). **Agent** : `a.source` = `github` (défaut : sa branche, pull, merge requests) ou `local` (répertoire local partagé : ni branche, ni pull, ni merge request ; son fichier de contexte est écrit dans `<localdir>/.agents/<Prénom>.md`). `local_agent(p, a)`.
- `repo_act` aiguille vers `local_act` si l'agent est `local` (ou s'il lit les fichiers d'un agent `local` via `agent:`). Lecture/liste libres (avertissement si le fichier est verrouillé par un autre) ; **écriture/suppression : verrou exigé**. Sans verrou explicite, le verrou est pris le temps de l'écriture (« éphémère »). Chemins bornés au répertoire (`locks.resolve`, liens symboliques compris) ; écriture interdite dans `.git/`, `.github/`, `.agents/` ; écriture atomique (fichier temporaire + `os.replace`). Chaque écriture est tracée dans `p.commits` (sha `local`).
- **Verrous** (`p.locks`, `p.lock_wait`, écrits par le serveur seulement) : exclusifs, par fichier. Actions `lock_file {paths}` (tout ou rien, jusqu'à 10 fichiers, **attend** que les autres agents aient libéré, `APM_LOCK_WAIT`), `unlock_file`, `get_locks`. File d'attente équitable (premier arrivé, premier servi ; attentes périmées ignorées après 15 s). Le verrou garde une sauvegarde du fichier d'origine (`data/lockbak/<projet>/`, ≤ 2 Mo) pour l'annulation.
- **Secours** : (1) verrou circulaire détecté à la demande (graphe d'attente, `locks.cycle`) → la demande qui boucle la chaîne est refusée aussitôt, avec la chaîne dans le message ; (2) expiration après `APM_LOCK_TTL` sans activité du détenteur, et libération des verrous « orphelins » (détenteur sans travail en cours depuis `APM_LOCK_ORPHAN`) par `tick` (même si le suivi est désactivé) ; (3) `recover()` libère tout au démarrage ; (4) fin de tâche (`finally` de `run_task`) libère tout ; (5) `stop_agent {agent, cancel, reason}` (agent principal) ou job `agent_stop` (utilisateur) : l'agent est interrompu (`locks.STOP` + `check_stop` dans `ask`/`do_act`/attente de verrou : un appel IA déjà parti n'est pas coupé, mais ses actions ne sont pas exécutées), ses verrous sont libérés, sa tâche passe `en attente` (`task.stopped`) ; avec `cancel`, les fichiers qu'il avait verrouillés sont remis dans leur état d'avant (fichiers créés supprimés) ; (6) `force_unlock {path}` (agent principal, refusé si le détenteur travaille encore) et jobs `lock_release` / `locks_clear` (utilisateur). Le diagnostic liste verrous, attentes et verrous circulaires. Panneau « Verrous de fichiers » dans l'onglet Équipe.
- Limites : verrous exclusifs (pas de verrou partagé en lecture) ; pas de commit git du répertoire local (c'est à l'utilisateur de le faire) ; un fichier modifié à la main pendant qu'un agent le verrouille n'est pas protégé.

## Conventions de travail
- **Champs de dialogue** (`chatInput`, ids `ci` onglet agent et `gi` vue globale) : `<textarea>` multiligne à hauteur auto (max 260 px, redimensionnable) ; Entrée envoie, Maj+Entrée insère un retour à la ligne (la saisie IME n'envoie pas). Le motif de refus d'une décision (`dn-`) est aussi un `<textarea>`.
- **Pièces jointes** (champs `ci`/`gi`) : fichiers texte glissés, collés ou choisis via « 📎 Joindre » ; lus côté navigateur (`addFiles`, état `ATT`, hors `data-keep`) puis ajoutés au message par `withAtt` sous forme de blocs `[Fichier joint : nom]` entourés d'une clôture de backticks adaptée. Aucun changement serveur : le job `say` reçoit un simple texte (le journal affiche donc le contenu joint). Limites : 200 Ko par fichier, 500 Ko au total ; les fichiers binaires (images, PDF…) sont refusés avec une alerte.
- Modifier `static/index.html` par remplacements ciblés ; vérifier la syntaxe JS (extraire le `<script>` et `node --check`).
- Lancer `python -m unittest discover -s tests` avant tout commit. Les tests n'utilisent ni réseau ni clé (faux GitHub, IA scriptée).
- Ne jamais committer `data/`, de token ni de clé API. Ne jamais tester sur le vrai dépôt sans supprimer ensuite les branches créées.
- Token GitHub requis : *Contents* et *Pull requests* en lecture/écriture (sinon fusion en 403 avec message explicite).

## Limites connues / suite prévue
- La détection de tâche « inactive » ne concerne que les tâches lancées par le moteur (`started`) ; une relance déclenchée par une réponse en chat (`say`) n'est vérifiée qu'au passage suivant du suivi si l'agent n'est pas passé par `run_task`.
- Services préconfigurés (`SERV` dans `static/index.html`, appliqués à un état neuf uniquement) : Claude `claude-sonnet-4-6` (`https://api.anthropic.com/v1`) ; Mistral `mistral-small-latest` (`https://api.mistral.ai/v1`) ; ChatGPT `gpt-4o` (`https://api.openai.com/v1`) ; Gemini et **Gemini-free** `gemini-3.8-flash` (`https://generativelanguage.googleapis.com/v1beta/openai`) ; DeepSeek `deepseek-chat` (`https://api.deepseek.com`).
- Les noms de modèles préconfigurés vieillissent (ex. `gemini-2.0-flash` a été retiré par Google, remplacé par `gemini-3.8-flash`) : à revérifier auprès du fournisseur ; une erreur 404 du service signale presque toujours un nom de modèle périmé.
- Pas de base de données ; sessions sans expiration ; clés API stockées en clair dans `data/`.
- Un serveur redémarré perd les travaux en cours (tâches marquées « Interrompu ») ; pas de file d'attente persistante.
- Les agents ne peuvent pas exécuter de code ni lancer de tests ; ils lisent/écrivent des fichiers du dépôt.
- Fusion à trois voies : si le navigateur reste très longtemps sans adopter l'état serveur (plus de 8 instantanés), le repli est « le navigateur gagne » (perte possible de données serveur récentes).
- Non testé : exécution sous Windows 11 ; fusions, merge requests, conflits et release contre le **vrai** GitHub (tout est testé contre un faux GitHub qui imite l'API) ; le token doit avoir *Contents* et *Pull requests* en écriture.
- **Spécification à valider (non implémentée)** : `docs/SPEC-git-local.md` — client git local intégré (worktree par agent, merges programmatiques, MR déduites de git). Son § 0.1 analyse les causes des agents « en attente » ; le **chantier 0** correspondant est **appliqué** (voir « Dialogue direct » ci-dessous).
- **Proposition (non implémentée)** : `docs/PROPOSITION-ETAPES-SYSTEME.md` — étapes de workflow `kind: system` exécutées par l'application sans IA (catalogue d'actions, paramètres, garde-fous). En attente de validation.
- **Dialogue direct (`say` → `ask_through`)** : si `ask` épuise ses `MAX_STEPS` étapes en plein travail, le retour non traité (`stats["pending"]`) est renvoyé à l'agent, sur au plus `SAY_ROUNDS`=4 échanges ; au-delà, un message système invite l'utilisateur à écrire « continue ». Avant, ce dernier retour (ex. contenu de fichiers lus) était perdu et l'agent répondait « je n'ai pas reçu… ». Les autres appelants d'`ask` (message d'agent à agent, `decide`…) ne reprennent pas encore `pending`.
- **Appels GitHub (`github.call_status`)** : `RETRIES`=3 nouvelles tentatives (`APM_GITHUB_RETRIES`), délai exponentiel ou `Retry-After`, plafonné à `MAX_WAIT`=30 s, sur 429 et 403 « rate limit » (toute méthode : le refus n'a rien exécuté) ; les 5xx et réseau injoignable ne sont réessayés qu'en GET (une écriture a pu être appliquée). Un 403 de permission n'est pas réessayé.
