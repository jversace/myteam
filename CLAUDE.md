# CLAUDE.md — contexte du projet « myteam »

> Lire ce fichier en premier : il évite de ré-analyser tout le code à chaque demande.
> **Le mettre à jour à chaque modification structurante** (route, champ d'état, action d'agent, décision d'architecture).

## But
Application de gestion de projets de développement par une **équipe d'agents IA** (Claude, Mistral, ChatGPT, Gemini, DeepSeek…). Tourne en local sur Windows 11 (usage actuel) ou sur un serveur Linux (plus tard). Langue de l'interface, des prompts et des commentaires : **français**.

## Stack et contraintes
- Backend : **Python 3.10+, bibliothèque standard uniquement** (aucun `pip install` ; ne pas en introduire sans décision explicite).
- Front : `static/index.html`, SPA **fichier unique** (HTML + CSS + JS, sans framework ni build), servie par le backend.
- Persistance : fichiers JSON dans `data/` (ignoré par git) : `users.json` (hash PBKDF2), `sessions.json`, `users/<user>.json` (**état complet** d'un utilisateur). Pas de base de données pour l'instant.
- Git/GitHub : **API REST GitHub** via `urllib` (pas de git local). Dépôt + token au niveau projet.
- Variables : `APM_PORT` (8000), `APM_HOST` (127.0.0.1), `APM_DATA`, `APM_ALLOW_REGISTER`, `APM_GITHUB_API` (tests), `APM_SUPERVISE_SECONDS` (passage du suivi, 60 ; 0 = désactivé). Windows : `start.bat`.

## API (JSON, `Authorization: Bearer <token>`)
- `POST /api/register|login` → `{token}` ; `POST /api/logout`
- `GET /api/state` → `{rev, ser, state}` ; `GET /api/state?ser=N` → `{same:true}` si rien n'a changé (sondage du front, toutes les 2 s)
- `PUT /api/state` `{rev, state}` → `{rev, ser, state}` : le serveur **fusionne** l'état du navigateur avec l'état courant (voir ci-dessous) et renvoie le résultat.
- `POST /api/service/test` `{serviceId}` : appel minimal au service IA (valide la clé). Les clés API se créent dans la console du fournisseur (aucun flux OAuth public ne permet de les générer : vérifié pour Anthropic et OpenAI) ; le front guide la saisie (`keyset`) et teste aussitôt.
- `POST /api/manual/answer` `{id,text}` / `POST /api/manual/cancel` `{id}` : réponse (ou annulation) d'un échange **manuel** en attente.
- `POST /api/job` `{type, projectId, ...}` : lance un travail en arrière-plan (un thread). Types : `say{agentId,text}`, `run_task{taskId}`, `onboard{agentId}`, `sync`, `release{version,notes}` (publication), `cycle_start{version}`, `mr_retry{mrId}`, `reset_usage`, `decide{decisionId,decision:accept|refuse|answer,note,fields,answer}`, `instr_add{scope,text}`, `instr_del{instrId}`. Le front fait `flush()` (PUT) avant chaque travail.

## Concurrence navigateur / serveur (important)
Le navigateur et le moteur modifient le même état. `store.put` fait une fusion **à trois voies** : base = dernier instantané reçu par le navigateur (`rev`, 8 gardés + celui servant de base), theirs = état disque, mine = état envoyé. Les listes d'objets avec `id` sont fusionnées par id (suppressions locales respectées, créations serveur conservées) ; en cas de vrai conflit sur une valeur, **le navigateur gagne**. Conséquences :
- Tout nouvel élément de liste doit avoir un `id`. Les listes sans `id` (`log`, `commits`, `history`…) sont écrites **uniquement par le serveur**.
- Champs écrits par le serveur : `log, commits, mrs, releases, cycle, conflicts, spec, releasing`, `agent.{history,notes,work,state}`, `task.{running,result,retry_at}`, tâches/bugs créés par les agents. Le navigateur ne doit pas les modifier (`ensure()` ne doit que **compléter** les champs manquants).
- Le front adopte l'état serveur (sondage ou réponse du PUT) sauf s'il a des modifications en attente ou une fenêtre modale ouverte.

## Modèle de données (état utilisateur)
`{services:[{id,name,url,kind,model,apiKey,account,pros,cons}], projects:[...]}`
Projet : `{id,name,open,desc,rules,spec,mainId,usage,ledger, repo:{url,branch,token}, cycle:{version,branch,started}, conflict_policy, conflicts[], roles[], agents[], tasks[], bugs[], modules[], log[], commits[], releases[], mrs[], releasing}`
- Agent : `{id,name,service,role,branch,canBug,talk[ids ; vide = tous, ["none"] = personne],notes,history[],state,work}` — **dépôt et token au niveau projet**, seule la **branche** varie par agent (peut être partagée).
- Tâche : `{id,parent,title,desc,who,status("à faire|en cours|terminée"),modules[],result,running,retry_at}`. Bug : `{id,t,d,sev,status,modules[],by}`. Module : `{id,name,desc}`.
- `log[]` : `{d,from,to,text}` = historique de **toutes** les discussions (Vous, agents, « Système », « Application »).
- **Coûts** : `ai.call_ai` renvoie un `Reply(str)` avec `.usage={in,out}` (Anthropic : `input_tokens`+cache, `output_tokens` ; OpenAI : `prompt_tokens`, `completion_tokens`). `engine.record_usage` cumule `{calls,in,out,cost}` dans `agent.usage` et `p.usage` (le total survit à la révocation d'un agent) et ajoute une ligne à `p.ledger` (300 max). Coût = tokens × tarifs du service (`service.pin` / `service.pout`, **$ par million de tokens, saisis par l'utilisateur**, jamais préremplis car les tarifs changent). Écrit par le serveur uniquement : **le front n'ajoute pas de valeur par défaut à `usage`/`ledger`** (sinon la fusion à trois voies écraserait les compteurs). Job `reset_usage`. Les agents en chat manuel ne sont pas mesurés.
- `ensure(p)` (front) complète les anciens états : **y ajouter tout nouveau champ**.

## Moteur d'agents (`engine.py`)
- `ask(u,pid,aid,text,frm,depth)` : boucle d'au plus `MAX_STEPS`=6 tours : prompt système (`sys_prompt`, reconstruit à chaque tour depuis l'état frais) + historique (30 derniers messages) → `call_ai` → blocs ```` ```action {json} ``` ```` (`parse_acts`) → `do_act`. Les **retours** (lecture de fichier, liste, réponse d'un autre agent, refus/erreurs) sont renvoyés à l'agent au tour suivant ; les écritures réussies sont seulement journalisées.
- Actions : `list_files`, `read_file`, `write_file`, `delete_file` (sur **la branche de l'agent** ; jamais sur la branche de base ; chemins validés par `safe_path`, `.github/`, `.git/` et `.agents/` interdits en écriture ; lecture tronquée à 12 000 car., écriture ≤ 200 000 car.), `message` (agents joignables ; le principal joint tous ; profondeur max 3 ; la réponse revient à l'expéditeur), `context`, `task_status`, `task`, `module`, `bug`, `bug_fix`, `bug_status`, `link_modules`, `ask_user`, `instruction`, `spec`, `get_progress` (voir « Droits, décisions et instructions »).
- **Toute nouvelle règle ou action se déclare dans `RULES` / `ACTIONS`** (elles alimentent le prompt système ET le fichier `.agents/<Prénom>.md`).
- Onboarding/synchronisation (`provision`) : crée la branche de l'agent si absente et pousse `.agents/<Prénom>.md` (règles équipe + projet, rôle, droits, actions, notes).
- Tâches (`run_task`) : quota 429/529 → agent `suspendu`, `retry_at`, reprise automatique par `threading.Timer` ; `recover()` au démarrage remet les compteurs à zéro, marque les tâches interrompues et replanifie les reprises.
- **Release et intégration** : voir « Workflow git » ci-dessous.
- Agent principal (`mainId`) : dialogue via le prompt de la Vue globale ; écrit à tous, crée les tâches, tient les spécifications, réalise MR + tag.

## Droits, décisions et instructions (`rights.py` + `engine.py`)
- **Capacités** (`rights.CAPS`) : `subtask, task_top, module, bug, bug_update, bug_verify, link`, chacune `free | approve | no`. Définies par **rôle** (`role.caps`, éditables dans l'onglet Rôles ; repli sur `DEFAULT_CAPS` par nom de rôle standard — **à garder synchronisé avec `DEF_CAPS` de `static/index.html`**), surchargeables par agent (`agent.caps`, **sans interface pour l'instant**). `rights.level()` applique ensuite : le principal ne peut pas être en dessous de `approve` pour `task_top`/`module` ; `agent.canBug` (ancien drapeau) réactive `bug` ; **autonomie du projet** `p.autonomy` : `prudent` (tout `free` de création → `approve`), `balanced`, `auto` (`approve` → `free` pour tâches de 1er niveau et modules).
- **Sous-tâches** : libres sous une tâche dont l'agent est responsable ou qu'il a créée (`rights.owns`), partout pour le principal ; profondeur max 4 ; doublons de titre refusés ; max `MAX_CREATE`=8 créations par échange.
- **Propositions** : un niveau `approve` ne crée rien : `engine.propose` ajoute une entrée à `p.decisions` (`kind: task|module|bug|question`, `status: attente|acceptée|refusée|répondue`, `payload`, `why`). Le navigateur **ne modifie jamais** `decisions` : il envoie le job `decide`, qui crée l'élément (`rights.create_from`, champs titre/nom/description modifiables) ou renvoie le refus/la réponse à l'agent par un `ask`.
- **Questions** (`ask_user`) : la tâche liée passe « en attente » (`task.blocked`) ; la réponse la remet « en cours », est transmise à l'agent, et si `structural` s'ajoute à `p.instructions`.
- **Bugs** : statuts `ouvert → en correction → corrigé → vérifié | rouvert` (`résolu` = ancien statut, traité comme fermé). Un bug crée (si absent) la tâche système « Corrections : <module> » (ou « Corrections (global) ») sans validation ; `bug_fix` y ajoute des sous-tâches (`task.bug`) ; quand toutes sont terminées via `task_status`/`run_task`, le bug passe à « corrigé » (`rights.on_task_done`). **Un changement de statut fait à la main dans l'interface ne déclenche pas cette mise à jour.**
- **Instructions partagées** : `p.instructions` (`{id,n,d,by,scope,text,active}`, portée `global | role:<nom> | agent:<prénom> | module:<nom>`), écrites par l'agent principal (action `instruction`) ou l'utilisateur (job `instr_add`) ; injectées dans le prompt de chaque agent concerné avec un bloc « Nouveautés » basé sur `p.seq` / `agent.seen_seq`. Les spécifications (`p.spec`, `p.spec_n`) sont aussi dans le prompt de **tous** les agents (6000 car. max).
- `get_progress` répond depuis l'état, **sans appel IA**. **Plafond de budget** : `p.budget` (client) ; `engine.check_budget` refuse tout appel API (erreur 402) quand `p.usage.cost` l'atteint.
- Écrits **uniquement par le serveur** (le front ne les modifie pas, et n'ajoute pas de valeur par défaut) : `decisions, instructions, seq, spec_n`, `agent.seen_seq`. Côté client : `autonomy`, `budget`, `role.caps`.

## Déblocage, réinitialisation et diagnostic (`engine.py`)
- **Pas d'« environnement d'exécution » d'agent** : un agent n'est qu'un historique de conversation (`agent.history`), des notes, une branche GitHub et des tâches ; tout passe par l'API GitHub, il n'existe aucun `.git` local ni état `MERGE_HEAD`. Un agent qui prétend le contraire hallucine une cause (cas réel : conflit resté ouvert → refus « conflit déjà en cours » → cause inventée → question absurde à l'utilisateur). Contre-mesures : règle explicite dans `RULES`, messages de refus factuels (`describe_conflict`), action `get_blockers`.
- **Conflits obsolètes** : `reconcile_conflicts` revérifie les conflits actifs (`OPEN_CONFLICT` = ouvert/escalade/pause) — plus aucun fichier en conflit **et** fusion réussie → clos (`close_conflict`/`_close_in` : statut, questions liées, tâche en attente), puis `after_conflict`. Appelé par `_tick` (toutes les `RECONCILE_EVERY`=300 s par conflit), avant tout refus dans `run_task` et `submit_mr` (`force`), et implicitement par un `pull` réussi. Un `pull` n'enregistre pas un second conflit si un est déjà actif.
- **Actions de l'utilisateur** (job `conflict_action{conflictId, action}`) : `check` (revérifier), `resolved` (déclarer résolu → suite), `retry` (relancer la résolution : résolveur de la règle, sinon agent principal), `abandon` (l'agent n'est plus bloqué ; un conflit persistant sera signalé de nouveau).
- **Réinitialiser un agent** (job `agent_reset{agentId, history, notes, branch, onboard}` → `agent_reset`) : annule ses attentes manuelles (`WAIT`), remet `work/state/seen_seq` à zéro, remet ses tâches en cours « à faire », clôt ses conflits (`abandonné`) et, avec `branch`, **remet sa branche sur la branche de travail** (`Repo.reset_branch`, force ; MR ouvertes → `annulée`), puis rejoue l'onboarding. Un appel IA déjà parti n'est pas interrompu (limite connue).
- **Diagnostic factuel** : `diagnose(p)` (sans IA) → `[{who, level: bloquant|attente|info, text, conflict?}]` ; exposé par `GET /api/diagnostic?project=` (bouton *Diagnostic des blocages* de l'onglet Équipe) et par l'action d'agent `get_blockers`. Tolérant aux états incomplets.
- **Décision « classer sans suite »** : `decide(..., "dismiss")` → statut `ignorée`, tâche liée débloquée.

## Autonomie : lancement automatique, tâches persistantes, reprise (`engine.py`)
Cause des « agents qui s'arrêtent » corrigée ici : avant, rien ne lançait les tâches, un tour d'agent s'arrêtait dès qu'une réponse n'avait pas d'action (ou après 6 étapes), la tâche passait alors d'office « à vérifier », et une exception laissait `running=True` pour toujours.
- **Lancement automatique** (`dispatch`, appelé par `tick` toutes les `APM_SUPERVISE_SECONDS`=60 s, et aussitôt après un événement via `spawn(tick)` : tâche créée, tâche vérifiée, MR fusionnée, job `decide`/`mr_retry`/`cycle_start`/`instr_add`) : une tâche `à faire` assignée démarre seule si ses dépendances sont satisfaites, si l'agent est libre (une tâche à la fois par agent), s'il n'est pas en chat manuel, sans conflit ouvert, sans échec en attente, sans enfants (tâche parente), budget non atteint. Réglage par projet : `p.autopilot = "off"`. Garde-fou `MAX_AUTO`=8 lancements par tâche, puis escalade à l'utilisateur (`auto_n`, `auto_escalated`). `tick` est protégé contre la réentrance (`TICKING`).
- **Tâche persistante** (`run_task`) : jusqu'à `MAX_ROUNDS`=6 tours de `MAX_ROUND_STEPS`=8 étapes. Après chaque tour, si la tâche est encore `en cours` : étapes épuisées (`stats["pending"]`) → on renvoie le retour non traité ; actions exécutées sans conclusion → `NUDGE` (« conclus avec task_status à vérifier, ou continue, ou demande ») ; deux tours consécutifs sans action → le travail est considéré rendu (`à vérifier`). Tours épuisés en plein travail → `à faire` + `resume` (relancée par le pilote avec « reprends là où tu t'es arrêté »). `ask(..., stats=, relog=, max_steps=)` renseigne `stats = {actions, pending}`.
- **Erreurs** : `quota`/`temp` → relances automatiques (`backoff`) ; `other` → `MAX_OTHER`=2 nouvelles tentatives avant `fail` ; `internal` (exception inattendue, interceptée par `run_task`) → `fail` + escalade directe. Exécution « fantôme » (`running` sans agent actif depuis `STALE_RUNNING`=15 min) réinitialisée par `_tick`. Contexte trop long (`_overflow`) → historique de l'agent compacté (4 derniers messages tronqués à 1500 car.) et nouvel essai. L'historique stocke les réponses tronquées à 6000 car. `say` (conversation) est relancé automatiquement après quota/erreur temporaire (`relog=False` : le message n'est pas journalisé deux fois).
- **Coordination entre agents** : `can_talk` — **par défaut un agent peut écrire à tous** (`talk` vide) ; `["none"]` = personne ; une liste = ces agents. Le prompt contient « Travail des autres agents » (`teamwork_text` : qui fait quoi, dépendances) ; le message de démarrage d'une tâche contient le contexte des **dépendances** (`dep_context` : compte rendu et branche des tâches dont elle dépend) et une consigne de coordination (`coordination_hint`) ; `RULES` impose l'initiative de coordination et la persistance après erreur.

## Workflow git : branche de travail par release (`engine.py` + `github.py`)
- **La branche principale (`repo.branch`) est réservée à la release finale.** Chaque release a une **branche de travail** `release/<version>` (`p.cycle`), créée depuis la principale par `cycle_start`. `Repo.work` = branche de travail du cycle, sinon la base ; `Repo.ensure_branch(b)` crée depuis `work`. Aucun agent n'écrit sur la base ni sur la branche de travail (`repo_act`, `provision`).
- **Pull** (`pull`) : fusion de la branche de travail dans la branche de l'agent (`POST /merges`) — automatique au démarrage de `run_task` et avant une MR, ou via l'action `pull`. États : `uptodate | merged | conflict | skip`.
- **Merge request** : `submit_mr` (action `merge_request`, ou automatique en fin de `run_task`) → pull, puis PR agent → branche de travail, enregistrée dans `p.mrs` (`{id,n,from,to,by,by_id,task,status: ouverte|fusionnée|conflit|refusée,note}`) → `review_mr` (thread) : l'**agent principal** (ou un agent `bug_verify`, jamais l'auteur) relit fichiers/commits et conclut par `mr_review approved|rejected` (`apply_mr_review` → `merge_mr`) ; pas de validateur possible → question à l'utilisateur (`decision.mr_review`). Refus : motif renvoyé à l'auteur.
- **Dépendances** : `task.deps` (ids) ; `run_task` ne démarre pas tant que `deps_unmet` n'est pas vide (tâche non terminée **ou** MR de cette tâche encore `ouverte|conflit`) ; `task.waiting` l'indique ; `merge_mr` logue les tâches débloquées.
- **Conflits** (`open_conflict`, `p.conflicts`) : détectés par `Repo.conflict_info` (fichiers modifiés des deux côtés depuis l'ancêtre commun et différents). **Règle du projet `p.conflict_policy`** : `ask` (défaut : décision à l'utilisateur, options `CONFLICT_OPTS` : auteur / agent principal / pause), `author` (l'auteur de la branche résout), `agent:<id>` (agent désigné) ; un agent en chat manuel n'est jamais désigné automatiquement. Le résolveur reçoit base / sa version / version de la branche de travail et répond par `resolve_merge {conflict, files:[{path, content}]}` : `merge_with_resolution` crée un **commit de fusion à deux parents** sur la branche de l'auteur (arbre de l'auteur + changements de la branche de travail, fichiers en conflit remplacés). Résolution incomplète ou avec marqueurs → refusée et renvoyée à l'agent ; 2 échecs, conflit trop gros (> 8 fichiers ou 60 000 car.) ou résolveur injoignable → escalade à l'utilisateur. Après résolution (`after_conflict`) : MR fusionnée, soumission reprise, ou tâche relancée. Pause : l'utilisateur résout sur GitHub puis `mr_retry`.
- **Publication** (`release`) : exige un cycle actif et aucune MR `ouverte|conflit` ; PR branche de travail → base fusionnée, tag + release GitHub, `p.cycle` supprimé. Sans dépôt configuré : enregistrement local seulement.
- Limites : les modes de fichier (exécutable) ne sont pas conservés lors d'une résolution ; `compare` GitHub est limité à 300 fichiers ; une branche d'agent créée avant le cycle se met à jour par pull.
- **Tests** : `tests/test_engine.py` embarque un faux GitHub à historique de commits (ancêtre commun, fusion à trois voies, conflits) — la classe `Integration` couvre ce workflow.

## Vérification des tâches et suivi (`engine.py`)
- **Statuts de tâche** : `à faire, en cours, en attente, à vérifier, terminée`. **Une tâche n'est jamais « terminée » d'office** : en fin de `run_task`, ou sur `task_status terminée` d'un agent (converti), elle passe `à vérifier` ; seuls `task_review accepted` (agent principal, ou agent avec `bug_verify` libre, jamais l'assigné) ou l'utilisateur la clôturent. Une validation manuelle dans l'interface contourne la vérification.
- **Vérification** (`review_task`, thread) : réservation atomique (`task.reviewing`), prompt avec description, compte rendu et **preuves** (`evidence` : commits de l'agent depuis `task.started`, ou « aucune écriture ») ; le vérificateur relit les fichiers via `read_file` + `"agent":"<prénom>"` (lecture seule sur la branche d'un autre agent, ou `"base"`). `apply_review` : `accepted` → `terminée` (+ `on_task_done` des bugs) ; `rejected` (motif obligatoire) → `à faire` et relance de l'agent avec le motif ; au `MAX_REVIEWS`=3ᵉ refus → escalade à l'utilisateur. Vérificateur muet 2 fois, ou personne d'éligible (principal en chat manuel…) → question de validation à l'utilisateur (`decision.review`).
- **Échecs d'appel** (`classify`) : `quota` et `temp` (réseau, 5xx) → **relance automatique** (`backoff` : délai du fournisseur puis 5, 15, 30 min, puis **toutes les heures** ; `temp` abandonné après `MAX_TEMP`=6 essais ; `quota` sans limite), l'agent est « suspendu » ; `budget` (402), `auth`, `model` → **escalade directe** à l'utilisateur (l'agent principal n'y peut rien) ; `other` → `task.fail`.
- **Suivi** (`tick`, boucle `supervisor_loop`, désactivable par projet : `p.supervision = "off"`) : replanifie les reprises manquantes, déclenche les vérifications en attente, repère les tâches en échec (`fail`) ou **inactives** (`en cours` lancée par le moteur, sans activité depuis `STALL_SECONDS`=10 min) ; il **interroge l'agent principal** (message « [Suivi automatique] », un seul par passage, délai de carence `SUP_COOLDOWN`=10 min) qui peut interroger l'agent (`message`), le relancer (`relaunch`, max `MAX_RELAUNCH`=3) ou remonter via `ask_user` ; après 2 interventions sans succès, ou si le principal est en chat manuel, **escalade directe** : décision à l'utilisateur (`add_escalation` : relancer / pause / abandonner, `decision.escalation`).
- **Décisions** : répondre à une question liée à une tâche **relance automatiquement la tâche** (`run_task` avec la décision) ; l'agent n'a plus besoin d'être relancé à la main. Escalade : option 1 ou texte libre → relance (le texte devient la consigne), option 2 → `en attente`, option 3 → abandon (`terminée` + `abandoned`).
- Champs de tâche écrits **par le serveur uniquement** : `started, touched, retries, retry_at, fail, reviewing, reviews, review_note, reviewed, review_fail, review_asked, review_err, sup_n, sup_ts, relaunch_n, abandoned, blocked` ; projet : `sup_err_ts`. Côté client : `supervision`.
- **Tests** : toujours patcher `engine.spawn` (threads d'arrière-plan : vérifications, relances) et vider `engine.TIMERS`, sinon des threads fuient d'un test à l'autre.

## Modes de connexion d'un agent (`agent.mode`)
- `api` (défaut) : `ai.call_ai` avec la clé du service. `manual` : **chat manuel**, sans API : `engine.manual_exchange` publie un prompt dans `p.pending` (`{id,agent,name,service,full,short,new,d}`), le thread **attend** (`WAIT`, 24 h) que l'utilisateur colle la réponse du chatbot (`/api/manual/answer`) ; les actions de la réponse sont ensuite exécutées comme d'habitude (les retours de lecture arrivent dans un nouveau prompt). `full` = instructions complètes (nouvelle conversation), `short` = suite (`agent.session` mémorise qu'une conversation existe).
- **Décision : on n'automatise pas les sites de chat** (claude.ai, chatgpt.com…) : pas d'API publique pour les abonnements grand public, conditions d'utilisation contraires (Anthropic l'applique techniquement), fragile. Alternatives gratuites sans automatisation de site : API à offre gratuite (ex. Gemini via AI Studio, avec limites) ou modèle local compatible OpenAI (ex. Ollama : service `kind:"openai"`, URL `http://localhost:11434/v1`, clé factice).
- `p.pending` est écrit par le serveur uniquement ; `recover()` le vide au démarrage.

## Conventions de travail
- Modifier `static/index.html` par remplacements ciblés ; vérifier la syntaxe JS (extraire le `<script>` et `node --check`).
- Lancer `python -m unittest discover -s tests` avant tout commit. Les tests n'utilisent ni réseau ni clé (faux GitHub, IA scriptée).
- Ne jamais committer `data/`, de token ni de clé API. Ne jamais tester sur le vrai dépôt sans supprimer ensuite les branches créées.
- Token GitHub requis : *Contents* et *Pull requests* en lecture/écriture (sinon fusion en 403 avec message explicite).

## Limites connues / suite prévue
- La détection de tâche « inactive » ne concerne que les tâches lancées par le moteur (`started`) ; une relance déclenchée par une réponse en chat (`say`) n'est vérifiée qu'au passage suivant du suivi si l'agent n'est pas passé par `run_task`.
- Les noms de modèles préconfigurés vieillissent (ex. `gemini-2.0-flash` a été retiré par Google, remplacé par `gemini-3.8-flash`) : à revérifier auprès du fournisseur ; une erreur 404 du service signale presque toujours un nom de modèle périmé.
- Pas de base de données ; sessions sans expiration ; clés API stockées en clair dans `data/`.
- Un serveur redémarré perd les travaux en cours (tâches marquées « Interrompu ») ; pas de file d'attente persistante.
- Les agents ne peuvent pas exécuter de code ni lancer de tests ; ils lisent/écrivent des fichiers du dépôt.
- Fusion à trois voies : si le navigateur reste très longtemps sans adopter l'état serveur (plus de 8 instantanés), le repli est « le navigateur gagne » (perte possible de données serveur récentes).
- Non testé : exécution sous Windows 11 ; fusions, merge requests, conflits et release contre le **vrai** GitHub (tout est testé contre un faux GitHub qui imite l'API) ; le token doit avoir *Contents* et *Pull requests* en écriture.
